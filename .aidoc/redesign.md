## 1. 노드별 계약과 개선안

### retrieve

| | 현재 |
|---|---|
| 상태 입력 | `query` · `inv.v_id` — DB 는 읽지 않는다 |
| 실질 입력 | Milvus `sm_scene_evidence` (v_id 필터) |
| 상태 출력 | `evidence`[{scene_id, hits, sim, snippets}] · `evidence_orphan` |
| 역할 | 질의 임베딩 → top-20 → 장면별 묶음 상위 8 + orphan 3 |

**문제**

- Milvus 행에는 `kind`(shot/stt/etc) · `shot_type` · `tags` · `labels` · `inning` ·
  `score_delta` · `h_id` · `s` · `e`가 전부 있는데, 검색은 일부만 요청하고
  (`h_id`·`score_delta`·`inning`은 요청조차 안 함) `_group_hits`가 나머지도 버린다.
  **다음 노드로 가는 건 `scene_id`·`hits`·`sim`·`text` 넷뿐.**
- 유사도 하한이 없어 무관한 히트도 전부 증거가 된다 (실측 v201: 0.51짜리 투수 시즌 성적).
- kind 균형이 없어 한 종류가 top-20을 점령한다 (실측 v201: **20건 전부 stt**).
  같은 장면에 훨씬 직접적인 화면 캡션이 있어도 못 올라온다.
- orphan 3줄이 "선곡 불가"라고 명시된 채 프롬프트를 차지한다 — 모델이 쓸 수 없는 정보다.
- 전 그룹이 `hits=1`이라 정렬 키 `(-hits, -sim)`의 앞 항이 무의미해진다.

**개선안**

1. `_group_hits`가 `kind`와 `s`를 스니펫마다 보존한다.
2. 장면 단위 사실(태그·라벨·이닝·점수)은 **Milvus 사본이 아니라 `inv.scenes`에서 조인**한다.
   색인 사본은 낡을 수 있고(`audit.md 1-1`), 인벤토리 표와 원천이 달라지면 서로 어긋난다.
   이러면 `output_fields`에서 `tags`·`labels`를 오히려 뺄 수 있다.
3. orphan 은 프롬프트에서 제외하고 API 응답·로그에만 남긴다.
4. kind 쿼터 — 종류별 상위 N건씩 뽑아 합친다.
5. 유사도 하한은 **절대값 대신 상대 기준**(최상위 대비 일정 폭). 임베딩 유사도 분포가
   질의마다 달라 절대 하한은 어떤 질의를 전멸시킨다. 질의 몇 종류로 분포를 재고 정한다.
6. ~~스니펫 절단 60자 → 120자(가능하면 문장 경계).~~ **처리(2026-08-24) — 절단 폐지.**
   프롬프트에 넣을 때 자르지 않고 색인 원문(청크 전문)을 그대로 싣는다. v203 실측:
   stt 719행 중 336행(47%)이 70자 초과라 절반이 잘려 나가고 있었다. 인벤토리 증가는
   +226자(스니펫 9건 기준) — 길이가 아니라 **개수 제한**(장면 8·종류당 2)이 병목이다.

**목표 형태**

```
장면 65 [범타] 8회 말 9-7→9-7 (득점 0) · 유사도 0.57
   화면 11621s: "외야수 44번이 담장 앞에서 타구를 잡아 던지는 장면"
   해설 11639s: "결정적인 수비 지금 할 말을 제가 잃었거든요, 순간적으로…"
```

### plan

| | 현재 |
|---|---|
| 입력 | `query` · `inv.inventory_text` · `budget` · `evidence` · `feedback` |
| 출력 | `spec`{mode, targets, view, budget, picked, reason} · `attempt` |
| 역할 | **그래프에서 유일하게 "무엇을 담을지"를 정한다** |
| 비용 | LLM thinking ~6분 (Qwen3.8) |

**문제 — 인벤토리에 판단 재료가 없다**

현재 한 행은 `65  범타  -  8회 말  9-7→9-7  14s`가 전부다. 그래서:

- **같은 범타 열 건이 구분되지 않는다.** `8회 말 2사 만루` 범타(위기 탈출)와
  `8회 말 무사 주자없음` 범타(평범한 아웃)가 완전히 같은 행으로 보인다.
  둘 다 `score_delta=0`이라 점수로도 못 가른다.
- `t_scene_baseball.score`에 팀명이 들어 있는데(`삼성 9-7 롯데`)
  `render_inventory`가 `.split()[1]`로 **가운데 토막만 떼어** `9-7`로 만든다.
  모델은 매 행마다 초/말 → 원정/홈 → 팀명 → 어느 쪽 점수가 올랐나를 3단 추론해야 한다.
- `t_scene_baseball.description`은 **v201 71건 전부 NULL** — 장면 설명문은 존재하지 않는다.

**있는데 안 쓰는 것**

`t_transition_baseball`에 전광판 상태가 통째로 있다 (실측 v201):

```
h9  2회 초  삼성1-롯데0  아웃2  주자 000  hint=득점+1
h15 3회 말  삼성1-롯데0  아웃2  주자 000  hint=아웃+2 주루
h65 8회 말  삼성9-롯데7  아웃1  주자 100  hint=아웃+1
```

`outs` · `balls` · `strikes` · `bases` · `away_team`/`home_team` 실명 · `hint`.
연결 경로: `t_scene_baseball.h_id` → `t_play_baseball.board_sec` → `t_transition_baseball.sec`.
**compose 는 이 테이블을 한 번도 조회하지 않는다** — `fetch_scenes`가 `t_play_baseball`을
LEFT JOIN 하지만 `end_sec` 하나만 가져온다.

**개선안 — 인벤토리에 상황을 넣는다**

```
번호  태그  라벨    이닝     상황         점수           길이
  9  홈런   역전    2회 초   2사 주자없음  삼성 0-0 → 1-0  44s
 15  범타   병살    3회 말   1사 1·2루    삼성 1-0        16s
 65  범타   -       8회 말   0사 1루      삼성 9-7        14s
```

주자·아웃카운트는 **라벨로 표현되지 않는 유일한 정보**라 이게 핵심이다.
`hint`(`아웃+2 주루`)는 이미 라벨(`병살`)로 파생돼 있어 중복이므로 넣지 않는다.

작업: `fetch_scenes` SQL 에 `t_transition_baseball` 조인 추가
(`outs`·`bases`·`away_team`·`home_team`) + `render_inventory` 수정.

> **주의**: 조인 키가 `t_play_baseball.board_sec = t_transition_baseball.sec`인데,
> 병합된 장면은 `h_id`가 앞쪽 것을 유지해 관측 시점이 실제 결과보다 이를 수 있다
> (`audit.md 6-1`). 만루 상황이 병합 전 값으로 나올 수 있으니 붙인 뒤 몇 건 눈으로 확인한다.

**그 밖의 문제** (`audit.md 2-2 · 2-3 · 2-4 · 2-5`)

- 응답 형식 검증이 없어 빈 응답도 "장면 없음"으로 통과 → LLM 장애와 구분 불가
- 예산 파싱이 첫 숫자만 집음 (`"1분 30초"` → 1)
- 선곡 번호 중복 제거 없음
- `</think>` 미종료 시 사고 과정이 답으로 파싱될 수 있음

### cutrank

| | 현재 |
|---|---|
| 입력 | `spec.picked` · `spec.budget` · `inv`(scenes·segs·utts) |
| 출력 | `picked`(cut 좌표 포함) · `spare` · `total` |
| 역할 | 점수순 정렬 → 클립 컷 → 예산 채움 (전부 결정적) |

**문제**

- 장면 하나가 예산보다 길면 통째로 `spare`로 밀려 0건 → "장면 없음"
  (**실측 comp 1**: v202 "홈런 모음" 예산 60초, 홈런은 74초 한 건 → 0클립)
- `RANK_LABEL_BONUS`에 삼중살·견제사·도루사·진루타·밀어내기·경기 종료·끝내기가 전부 없어
  가산 0. 가장 드문 삼중살이 병살(+2)보다 낮게 평가된다.
- `CUT_RECIPE`에 `견제` 없음 + `LABEL_EXTRA_SHOTS`에 `견제사` 없음 →
  견제사 장면이 "투수가 공 던지는 3초"로 나가고 주자 태그아웃이 빠진다.
- `LABEL_EXTRA_MAX_SEC`가 부분 상한이 아니라 **체인 종결자**로 동작 —
  상한 초과 샷 하나가 뒤따르는 정상 샷까지 죽인다.

**개선안**

1. 예산보다 긴 단일 장면은 **최소 한 건은 담되 초과를 알린다** (또는 질의가 pinpoint 면 허용).
2. 라벨 가산 보강 — 다만 vocab.py 원칙("근거 없이 값을 바꾸지 말 것")에 따라
   실측 근거를 만든 뒤 정한다. 후보: 끝내기·경기 종료·삼중살.
3. `견제` 레시피와 `견제사` 여운 샷 추가.

### route / feedback / backfill

| | 현재 |
|---|---|
| route 입력 | `picked` · `spare` · `total` · `spec.budget` · `attempt` |
| feedback 출력 | `feedback` 문자열 → plan 재진입 (최대 1회) |
| backfill 출력 | `picked`(충원) · `total` |

**문제**

- `feedback` 메시지가 원인과 무관하게 "어휘를 다시 번역하라" 고정 — 예산 절단으로 0건이
  된 경우 재선곡이 문제를 못 고친다.
- `underfill` 판정에 `not spare` 조건이 있어, 예비가 남으면 심한 미달에도 backfill 을 건너뛴다.
- backfill 이 조건 미달로 무동작해도 로그가 없다 — route 의 "backfill 만" 로그와 합쳐 보면
  충원을 시도한 것처럼 읽힌다.

### endfix

| | 현재 |
|---|---|
| 입력 | `picked` 각 클립 끝 · 그 뒤 `inv.utts` 최대 4건 |
| 출력 | `picked`(끝 이동) · `endfix_moved` · `total` |
| 비용 | LLM thinking ~2분 |

**문제**

- **예산 재검사가 없다** — 900초 요청이 947~1018초로 나온 유일한 원인.
- 클립 간 겹침을 보지 않는다.
- **프롬프트도 응답 원문도 로그에 남지 않는다** — 처분 결과만 남아 재현 불가.
- 얻는 것은 클립당 최대 12초. 실측 v201 comp 3: 8건 이동, 합계 +61초.

**개선안**

예산 상한을 넘기면 이동을 기각하거나, 초과분만큼 뒤쪽 클립을 줄인다.
그 전에 **이 노드를 LLM 으로 유지할 이유가 있는지** 판단한다 —
cut 에 이미 결정적 꼬리 스냅(`DIALOGUE_TAIL_MAX_SEC=9`)이 있고, endfix 는 그것이 놓친
잔여만 본다. 결정적 규칙으로 대체하면 2분과 비결정성이 함께 사라진다.

### verify

| | 현재 |
|---|---|
| 입력 | `spec` 요약 · `picked` 패킷(태그·라벨·샷·대사) |
| 출력 | `suspicions` · `status`="ok" |
| 비용 | LLM thinking ~3분 |

**문제 — 출력물을 바꾸지 않는다**

기각권이 없어 `기각`에 번호가 와도 클립은 그대로 간다. `판정` 값도 코드가 읽지 않는다.
즉 **이 콜의 결과가 출력물에 영향을 주는 경로가 없다.** 그런데도 실패하면 예외가 전파돼
이미 확정된 클립이 통째로 버려진다 (`audit.md 5-1`).

**개선안**

- 실패를 삼켜 편성을 살린다 (소견 없이 `status=ok`).
- thinking 을 끄거나 선택적(`verify=false`)으로 만든다 — 3분을 항상 쓸 이유가 없다.
- 남길지 자체를 재검토: 리포트 가치가 실제로 쓰이는지 확인 후 결정.

## 2. 구조적 결론 — 불변식 층이 없다

득점 장면을 반드시 담는다 · 예산을 넘기지 않는다 · 같은 장면을 두 번 넣지 않는다.
이 셋은 **취향이 아니라 최소 요건**인데, 전부 plan 의 그때그때 판단에 맡겨져 있다.

예산 배선을 고치자 이닝 커버리지가 100%가 되면서 득점 포함이 53%까지 떨어진 것이 그 증거다.
프롬프트를 어느 쪽으로 밀어도 반대쪽이 무너지고, 코드가 균형점을 강제하지 않는다.

**제안: LLM 은 제안하고 코드가 강제한다.**
`cutrank` 뒤에 결정적 후처리 노드를 하나 두어

- 득점 장면(`score_delta > 0`)과 결정 라벨(역전·동점·끝내기·경기 종료) 중 누락분을
  예산 안에서 우선 회수
- 예산 초과분 정리
- 중복 제거

를 보장한다. 그래프를 갈아엎는 재설계가 아니라 **노드 하나 추가**다.
선곡기(LLM)의 판단 자체는 작동하고 있으므로(v201 실측: 빠진 7이닝 전부 득점 0 =
정당한 제외, 6회초·7회말 쏠림도 실제 득점 구간) 대체하지 않는다.

## 3. 착수 순서

각 단계는 **단독으로 배포·측정 가능**해야 하고, 직전 단계 대비 `eval_compose.py` 수치로
효과를 증명한 뒤 다음으로 넘어간다.

### Phase 1 — 입력 보강 (재료를 준다)

1. 인벤토리에 상황 추가 (`fetch_scenes` 조인 + `render_inventory`) — 아웃·주자·팀명
2. 증거 블록 개선 (`_group_hits` + `render_evidence`) — kind·시점 표시, 사실은 `inv.scenes`
   조인, orphan 제외, 스니펫 120자

검증: 5경기 재실행 → 득점 포함률·결정 라벨 포함률. 상황 정보가 붙으면 "2사 만루 범타"
같은 고긴장 장면이 선곡에 들어오는지도 본다.
bench4 byte 등가 게이트는 어휘 때처럼 **의도된 이탈**로 명시하고 나머지는 유지.

### Phase 2 — 불변식 층 (요건을 강제한다)

3. `cutrank` 뒤 결정적 후처리 노드 — 득점·결정 라벨 회수, 예산 정리, 중복 제거

검증: 득점 포함률이 100%에 수렴하는지. 이닝 커버리지가 후퇴하지 않는지.

### Phase 3 — LLM 콜 정리 (비용을 줄인다)

4. endfix 결정적 대체 또는 예산 재검사 추가
5. verify 실패 흡수 + thinking 해제/선택화

검증: 품질 지표 불변 + 편성 소요 시간. 현재 11~16분에서 절반 이하가 목표.

### Phase 4 — 검색 품질 (자유 질의)

6. kind 쿼터 · 유사도 상대 하한

검증: `"구자욱 홈런"`·`"다이빙 캐치"` 같은 자유 질의로 후보 장면 수와 정확도.

> **선행 판단 필요**: 자유 질의가 과제 목표에 포함되는가?
> 이닝 하이라이트 질의는 증거를 거의 쓰지 않고 태그·점수만으로 풀린다.
> 포함되지 않으면 Phase 4 는 후순위로 내린다.

### 병행 — 관측 가능성

7. 실행 단위 트레이스 (편성 1건 = JSON 1개): 노드별 입출력 값, LLM 3콜의 프롬프트·응답·
   thinking 전문, `finish_reason`, 노드별 소요.
   전역 `LOG_LEVEL=DEBUG`는 plan user 프롬프트만 3,786자(v201)라 운영 로그를 덮는다.
   A/B 시 "같은 입력에 왜 다른 선곡이 나왔나"를 파일 diff 로 보려면 이게 필요하다.

## 4. 미결정

- **라벨 가산치**(끝내기·경기 종료·삼중살) — 실측 근거를 만든 뒤 정한다.
- **endfix 존치** — 결정적 대체로 품질이 유지되는지 측정 후.
- **verify 존치** — 리포트가 실제로 소비되는지 확인 후.
- **Phase 4 우선순위** — 자유 질의가 목표인지에 달렸다.
- **인벤토리에 샷 캡션 요약을 붙일지** — `t_scene_baseball.description`은 비어 있고
  `t_segment.summary`는 있다(현재 `fetch_shots_all`이 안 가져옴). 71장면 전체에 붙이면
  프롬프트가 크게 늘어 plan 시간이 증가한다. Phase 1 효과를 본 뒤 판단.
